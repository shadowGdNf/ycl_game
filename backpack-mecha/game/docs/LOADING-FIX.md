# dev.6.1：手机图片加载与灰屏修复

日期：2026-10-29。基线：`7880a2c`（dev.6）。规则版本仍为 `0.1.1`。

## 已定位的启动缺陷

原来的 `boot()` 先显示可操作首页，再等待 `renderer.load()`，最后才启动动画循环。加载器在 manifest 和四张必需图片上没有超时：任一请求一直等待时，玩家仍可开始远征，但战斗画布没有渲染循环。图片报错时也只显示短暂提示，无法原地重试，且 manifest 必须等所有图片成功才交给渲染器。

这是代码中可确认、与用户 Android Chrome 灰屏现象吻合的路径；未读取用户手机的网络/控制台日志，不能断言其设备只遇到了这一种故障。线上 HTML 在本次检查中返回 HTTP 200，GitHub Pages 缓存头为 `max-age=600`。不能据此推算用户所在网络的访问速度。

## 修改

- 保留 PNG 原稿，单独生成 WebP 发布副本，质量参数 82；尺寸、透明通道、86 个采样区保持一致。普通构建直接使用已提交的副本，只有重新压缩美术需要 Pillow/WebP。
- 关键图片由 HTML 提前请求；装饰地面仍在战斗时延迟加载。地面失败时保留基础地面，不阻止规则运行。
- 画面循环不等待图片网络请求。必需图片未就绪时，启动新局/继续游戏/进入战斗均受保护；切换语言或模式后保护仍生效。
- 显示 `0/4` 至 `4/4` 的加载状态；每次 manifest/图片请求 15 秒超时，自动重试一次。失败后显示持久提示及手动重试，保留已经成功的图片。
- 图集文件名携带内容哈希；入口和整个模块依赖图、CSS、manifest 使用同一构建内容版本，减少新旧缓存混用。
- Canvas 圆角路径有兼容实现，不依赖 `roundRect` 存在。未处理的帧异常会暂停、尝试存档并提示刷新，禁止继续开启无渲染的战斗。

## 验证

- `npm run check`、`npm test`（110/110）、`npm run build`、`npm run bundle:check`、`npm run art:check`、`git diff --check HEAD` 通过。
- 新增加载器测试覆盖图片失败、无响应超时、manifest 超时、重复调用合并、保留已成功资源后的重试、装饰地面失败与旧 Canvas 圆角路径。
- 内置浏览器 390×844 视口：正常进入战斗，机甲与地面可见，无 console error/warn。
- `/broken/`：模拟机甲图集两次 503，显示持久错误和禁用启动按钮；点击重试后恢复，可进入战斗。
- `/slow/`：图片延迟 8 秒，显示进度并禁用新局/续局；期间切换模式仍保持禁用，加载完成后恢复。
- `/legacy/`：删除主画布与离屏画布的 `roundRect`，390×844 下仍能继续存档并绘制战斗，无 console error/warn。
- 子目录 `/broken/`、`/slow/`、`/legacy/` 均使用相对路径正常取资源。

故障页面可用 `node scripts/serve-loading.mjs` 在本机 4184 端口复验；重启该测试服务会重置两次 503。夹具不进入发布包。本地截图保存在 `qa/loading-*.jpg`（按既有规则不纳入 Git）。

## 发布与边界

本记录完成时已生成源码与对应 `dist/`，尚未提交或推送本次修复。只有将它们发布到现有 GitHub Pages 后，原试玩链接才会使用新版。可以先用 `npm run dev` 在本机试玩。

上述是自动化测试和桌面浏览器手机视口验证，不是用户 Android Chrome 真机测试，也没有测量移动网络首次访问秒数。WebP 副本采用有损颜色压缩，原稿和透明通道保留。若发布后在用户网络上访问 GitHub Pages 仍慢，需要单独评估可访问性更好的静态托管/CDN；本次没有迁移域名或存档来源。
