# REA × Codex 中文使用指南

本文针对官方 npm 发布包 `rea-agents@6.7.0`，核对日期为 2026-10-23。用户入口是 `$reverse-engineer-anything`；REA 的 MCP 服务名为 `rea`。

## 它解决什么问题

REA 把逆向工具包装成智能体可调用的 MCP 服务，也提供同一套工作流的 CLI。典型流程是：指定应用或制品 → 选择分析方式 → 找入口、引用和数据流 → 保留证据 → 解释功能或实现并验证类似功能。

- **技能**负责调查方法、目标分流、结果分页和证据要求。
- **REA MCP / CLI**负责执行分析、管理会话和组织 Evidence。
- **分析引擎**负责特定格式的反编译或观测，按目标另行配置。

它适合缺少源代码的已发布软件、二进制、安装包和行为研究。已有完整源码时，直接阅读仓库通常更合适。伪代码、模块关系和静态调用候选并不等于完整原始源码，也不证明某条路径实际执行过。

## 选哪条路线

| 目标 / 问题 | REA 入口 | 额外条件与边界 |
| --- | --- | --- |
| Electron / ASAR / 已解包 JavaScript | `analyze_javascript_application` | 无需原生反编译器；识别模块、导入、preload、IPC、source map 等静态关系 |
| PE / ELF / Mach-O 原生代码、原生游戏函数 | `open_binary` → 函数、字符串、反编译与交叉引用 | Hopper / Ghidra / IDA 等适配器；按实际 `tool_availability` 选择 |
| .NET / Unity Mono 程序集 | `inspect_managed_artifact` → `inspect_managed_members` | 静态读取 PE/CLI 元数据与 CIL，不加载程序集；IL2CPP 和 NativeAOT 不能直接按普通 .NET 程序集处理 |
| APK 内 Java / Kotlin 逻辑 | `inspect_android_package` → 类、方法与引用 | 此发布版配套指引要求 headless JADX MCP JAR 0.7.1 和 Java 17+ 完整 JDK；`REA_JADX_MCP_JAR` 指定路径 |
| ZIP / APK / IPA / DMG 等包内资源 | `open_binary` → `inspect_artifact` | 先查看清单；需要导出时指定新的输出目录 |
| 已保存 HAR / SAZ 等网络记录 | `inspect_web_network_capture` | 离线证据；不会自动重放请求，也不代表当前服务端完整行为 |
| 网站或 Electron 运行时 | 浏览器 / Electron target 与 scenario 工具 | 需要可连接的运行时；启动、点击、输入等按本次任务范围执行 |
| 固件、WASM、抓包、设备等专用格式 | 按服务端实际工具列表选择 | 可能依赖 Linux、WABT、TShark、ADB、Binwalk 等；工具出现在列表中不等于本机条件齐备 |

本机是 macOS arm64，Node 为 24.21.0。npm 发布包 6.7.0 的要求是 `^22.19.0 || ^24.11.0 || >=26.0.0`，当前 Node 满足要求。GitHub `main` 的同版本字符串下已有更高的 Node 要求和新增功能，不能据此认定 npm 包也具备这些能力。

## 直接在 Codex 中使用

接入后重启 Codex / 重新建立 MCP 连接。技能可能先被发现，但当前已运行的聊天不能仅凭配置文件写入就视为已连接。可先发送：

```text
用 $reverse-engineer-anything 检查 REA 是否已连接，说明当前能用的分析类型。
```

给出**目标绝对路径、具体问题和期望输出**，比“逆向整个应用”更容易得到可验证的结果：

```text
用 $reverse-engineer-anything 分析 /absolute/path/app.asar。
追踪搜索功能从渲染进程、preload、IPC 到主进程的调用链。
先做静态分析，列出关键文件和位置、Evidence ID、推断和未确定项。
```

```text
用 $reverse-engineer-anything 分析 /absolute/path/game.exe 的音效声像计算。
定位相关字符串和函数，解释输入、计算步骤和输出，引用地址与汇编证据。
如需原生引擎，使用已配置且支持该格式的 provider。
```

```text
用 $reverse-engineer-anything 比较 /absolute/path/v1.asar 与 /absolute/path/v2.asar。
只研究导出功能的变化；给出增加、删除、行为变化候选及证据覆盖不足的部分。
```

```text
用 $reverse-engineer-anything 分析 /absolute/path/MyApp.apk 的本地存储逻辑。
定位入口类、方法和引用；区分清单声明、反编译观察与运行时结论。
```

```text
用 $reverse-engineer-anything 研究 /absolute/path/target 的指定功能，
然后在当前项目实现类似行为，并用测试说明已验证的输入范围和差异。
```

## CLI 用法

本指南使用固定版本的 `npx`，不依赖全局 `rea` 命令。以下路径均为示例，替换为目标的真实绝对路径。结果文件应写到新的输出位置，避免覆盖旧证据。

### 查看实际功能与诊断

```bash
npx -y rea-agents@6.7.0 --help
npx -y rea-agents@6.7.0 doctor --client codex --json
npx -y rea-agents@6.7.0 doctor --skill --json
npx -y rea-agents@6.7.0 mcp doctor --json
npx -y rea-agents@6.7.0 providers --json
```

`doctor --client codex` 验证客户端配置；`mcp doctor` 检查独立 MCP 进程启动。两者都不能证明当前聊天已经加载工具。总览 doctor 可能因缺少可选引擎而报告不健康，应查看当前任务对应的检查项。

### JavaScript / Electron 静态分析

```bash
npx -y rea-agents@6.7.0 analyze-javascript-application \
  /absolute/path/app.asar --json > app-evidence.json
```

目录也可以作为目标。大型应用完整 JSON 可能很大，应先保存，再投影摘要，不要把整个文件直接塞进聊天上下文。

使用现有 Node 将保存的 Evidence 包装为发布版支持的 `inline` 请求：

```bash
node --input-type=module <<'JS'
import fs from 'node:fs';
const evidence = JSON.parse(fs.readFileSync('app-evidence.json', 'utf8'));
fs.writeFileSync('view-request.json', JSON.stringify({
  source: { kind: 'inline', evidence },
  view: { kind: 'summary' }
}));
JS
```

```bash
npx -y rea-agents@6.7.0 inspect-analysis-view view-request.json --json
```

该办法会在本地读取完整 JSON，大文件仍需足够内存。GitHub main 文档中的 `source.kind: "evidence-file"` 不应套用到本次 6.7.0 发布包；这里使用的 `inline` 方式已通过样本验证。

在 MCP 中优先使用 `detail: "summary"`，沿返回的 `parent_evidence_id` 查询。模块分页后使用返回的 `node_id` 精确选择；不要猜 ID，同一路径可能对应多个图节点。MCP 保留引用通常限于同一连接，跨会话需要导出 Evidence。

### 原生代码（已配置 Ghidra 时）

```bash
npx -y rea-agents@6.7.0 doctor --provider ghidra --json
npx -y rea-agents@6.7.0 analyze /absolute/path/game.exe --provider ghidra --json
npx -y rea-agents@6.7.0 search /absolute/path/game.exe 'audio' --provider ghidra --json
npx -y rea-agents@6.7.0 function /absolute/path/game.exe main --provider ghidra --json
npx -y rea-agents@6.7.0 decompile /absolute/path/game.exe 0x1000 --provider ghidra --json
npx -y rea-agents@6.7.0 xrefs /absolute/path/game.exe 0x1000 --provider ghidra --json
```

`main` 和 `0x1000` 是占位示例，必须换成实际返回的函数或地址。多个 provider 同时支持目标时显式选择。Ghidra 通常通过 `GHIDRA_INSTALL_DIR` 和相应 JDK 配置；把环境变量设置在启动 MCP 的配置中才能影响该服务，修改另一个终端的环境不会改变已启动进程。

### .NET 程序集

```bash
npx -y rea-agents@6.7.0 inspect-managed-artifact /absolute/path/Assembly.dll --json
npx -y rea-agents@6.7.0 inspect-managed-members /absolute/path/Assembly.dll --json
npx -y rea-agents@6.7.0 inspect-managed-members \
  /absolute/path/Assembly.dll --type Example.Parser --json
```

`Example.Parser` 应替换为成员清单中返回的完整类型名。

## 结果应怎样阅读

优先看 `normalized_result`，并保留 `evidence_id`、目标摘要、来源位置、coverage、limitations 和 unknowns。调查报告应分别说明：

1. **观察到的事实**：具体文件、地址、指令、字符串、记录或运行步骤。
2. **推断**：事实如何支持一个行为假设，是否还有其他解释。
3. **未确定项**：动态分发、缺失模块、混淆、未覆盖输入或缺失依赖。
4. **实现与验证**：新实现的设计选择，以及实际测试覆盖的行为。

纯静态分析不执行目标应用；运行时抓取会执行目标或与其交互。REA 的进程捕获不是隔离沙箱。分析在本机进行，但返回给智能体的工具内容仍进入该智能体的数据处理流程。

## 更新与恢复

更新前先检查新版要求，并预览限定为 Codex 的变更：

```bash
npm view rea-agents version engines --json
npx -y rea-agents@latest setup --client codex --dry-run --json
```

确认该计划适用于本次更新后，用**同一个已核对的版本号**执行 `setup --client codex --yes`，再重启客户端。不要使用 `--all-detected` 扩大到其他客户端。REA 的 setup 会维护配置备份并安装匹配技能；直接从 GitHub main 单独更新 skill 可能造成服务端与指引不一致。

出现问题时按层定位：

| 现象 | 下一步 |
| --- | --- |
| 技能可见，但没有 REA 工具 | 检查 Codex 注册与 MCP 启动日志，然后重启 / 重连 |
| `provider_unavailable` | 诊断所选引擎，不要反复重装 skill |
| `ambiguous` | 从返回的候选 provider 中明确选择 |
| 大结果被截断 | 查询保留 Evidence 的摘要 / 分页，或导出完整结果 |
| Ghidra 超时 | 查启动诊断与分析状态；不要无限重复冷启动 |
| macOS Swift / Clang 缓存报 `Operation not permitted` | 检查诊断中的真实写入路径。此次首次分析需要写入 `~/.cache/clang/ModuleCache`；按宿主权限机制允许该准备步骤后测试通过。不要仅凭后续级联的 SDK 错误就重装工具链 |
| 客户端权限拒绝 | 处理实际权限原因，不修改或绕过宿主审批策略 |
